# AI 产品经理研究助手

使用本 Skill，将初始产品信号转化为有证据支持的市场、用户与机会判断，并按需导出研究结果。

## 触发边界

仅当用户明确输入完整口令 **AI产品经理工作开始** 时，启动完整工作流。口令后可以直接附带产品想法、指定产品、用户需求或调研深度。

不要因为普通请求涉及产品管理，就自动扩展为完整工作流。如果用户显式调用 `$ai-product-manager-research`，视同输入启动口令。

## 流程状态管理

在整段对话中持续记录当前项目、启动模式、调研深度、已确认计划、已完成模块、关键假设和资料来源。

- 用户输入 `继续`：从当前停顿点恢复。
- 用户输入 `修改调研计划`：返回计划阶段；计划重新确认后，重做所有受修改影响的分析。
- 用户输入 `重做市场调研`、`重做用户画像` 或 `重做机会点`：只重做指定模块，并更新依赖该模块的后续结论。
- 当前流程尚未结束时再次收到启动口令：先询问用户要继续当前项目，还是开始新项目。
- 不得混用不同项目的证据、假设或结论。

## 1. 确定启动模式

优先根据启动口令后的内容识别模式。如果无法识别，让用户从以下三种模式中选择一种：产品想法、指定产品、用户需求。如果多个模式都可能成立，选择最符合用户目标的模式；无法可靠判断时再让用户选择。

确定模式后，必须先取得与该模式对应的核心信息：

- 产品想法：用户的具体产品想法
- 指定产品：具体产品名称
- 用户需求：具体用户需求

核心信息不可跳过，也不能由默认值替代。用户提交核心信息的消息本身就是继续执行的指令：收到后必须在下一次回复中立即提出补充问题，或直接开展该模式规定的后续工作。不得只复述或确认收到的信息后停下，不得询问“是否开始”，也不得要求用户再输入 `开始`、`继续` 或 `确认`。如果启动口令中已经包含足够具体的核心信息，同样立即继续。

用户回答补充问题后，也应立即生成调研计划，不得再增加“开始调研计划”等口令。调研启动阶段唯一的确认节点，是调研计划生成完成后等待用户明确确认；用户确认前不得进入正式市场调研。研究完成后仅询问调研结果的导出需求。

### 产品想法

如果用户选择了“产品想法”但尚未说明想法是什么，必须先单独要求用户提供具体的产品想法。获得产品想法前，不得进入结构化补充提问或生成调研计划。用户一旦提供想法，下一次回复必须直接进入自适应补充提问，不得要求用户再输入开始口令。

获得产品想法后，按以下规则进行自适应提问：

1. 第一轮一次提出不超过 4 个高价值问题，以适配结构化提问卡片的容量限制。如果当前环境的卡片上限少于 4 个，则遵守更低的工具限制。
2. 最多再进行一轮自适应追问。
3. 除“产品想法本身”外，所有补充问题均非必答。每道补充问题都要明确提供或标注 `跳过` 选项；用户也可以回复 `全部跳过`。
4. 对于跳过或未回答的补充信息，采用符合中国市场的合理默认情况，并记录为假设。
5. 信息足以形成有效调研计划后，立即停止提问。

优先了解预期目标、目标用户、使用场景、产品形态、商业意图和真正影响方案的限制条件。不得机械重复询问用户已经提供的信息。

### 指定产品

如果用户选择了“指定产品”但尚未提供产品名称，必须先单独要求用户输入具体产品名称。产品名称不可跳过。用户一旦提供名称，下一次回复必须直接检索最可能对应的产品公开资料并自动生成调研计划，不得要求用户再输入开始口令，也不进行前置问卷。

如果产品名称存在歧义，不增加计划前的确认步骤，而是自行选择最可能的对象。在调研计划中明确写出识别到的公司或产品主体、官网、相关版本或地区，以及做出该判断的依据，供用户在计划确认阶段纠正。

### 用户需求

如果用户选择了“用户需求”但尚未提供具体需求，必须先单独要求用户说明具体需求。获得具体需求前，不得开始补充提问或生成调研计划。具体需求不可跳过。用户一旦提供需求，下一次回复必须直接进入相关补充提问，不得要求用户再输入开始口令。

获得具体需求后，围绕需求背景、深层痛点、受影响人群、当前替代方法和期望结果进行自适应补充提问。第一轮一次不超过 4 个问题；如果当前环境的结构化提问卡片上限更低，则遵守工具限制。最多再追问一轮。除“具体需求本身”外，每道补充问题均提供 `跳过` 选项；被跳过的信息按中国市场的合理情况补全并标记为假设。随后结合用户提供的需求和补充信息生成调研计划。

## 2. 生成并确认调研计划

使用 [references/output-templates.md](references/output-templates.md) 中的“调研计划”模板。写明启动模式、对研究对象的理解、核心研究问题、研究范围、研究方法、拟对比对象、计划交付物和关键假设。

展示调研计划后，**必须停下并等待用户明确确认**。用户确认前不得开始完整市场调研。如果用户修改计划，更新后再次请求确认。

## 3. 连续完成调研与分析

调研计划确认后，不设置中间确认点，连续完成以下三个模块：

1. 市场调研
2. 用户画像
3. 产品机会点与风险

进入本阶段前，先阅读并遵守 [references/research-standards.md](references/research-standards.md)，同时按需读取 [references/output-templates.md](references/output-templates.md) 中对应模块的模板。

市场调研阶段必须实际联网检索。使用当前环境可用的搜索与网页浏览能力，不得只依赖模型已有知识。如果无法联网或关键资料无法访问，应说明缺失的覆盖范围，并询问用户是稍后重试，还是基于明确受限的资料继续。不得虚构来源。

默认采用标准版调研。如果启动口令中包含 `快速版`、`深度版`，或用户之后提出相应要求，则调整深度：

- 快速版：只聚焦对关键决策影响最大的证据。
- 标准版：覆盖主要市场信号、代表性竞品、典型用户反馈和重要趋势；当新增资料不再显著改变结论时停止。
- 深度版：扩大资料类型、竞品、用户反馈、冲突观点和验证方案的覆盖范围。

不强制凑固定的来源数量。优先保证决策价值、来源质量、来源多样性和证据饱和度。

## 4. 研究结论与后续交接

完成市场调研、用户画像、产品机会点与风险后，总结研究结论、证据局限和仍需验证的假设。本 Skill 的交付物限于调研计划和上述研究模块，不制作 MVP 功能清单或 PRD，也不在研究结束后主动询问是否生成这些文档。

用户明确要求继续制作 PRD、MVP 功能范围与优先级、版本方案或自有产品原型时，交给 `edu-pm-workflow`（产品经理工作流）。交接信息包括产品方向、目标用户与场景、需求证据、竞品事实、机会假设、关键限制、资料来源、检索日期和待确认项；已有明确产品决策单独标记。研究假设不能直接转换为已确认需求。

机会点中的验证建议可包括访谈、概念测试和付费意愿实验等研究方法；产品功能选取、验收标准及版本范围由产品经理工作流定义。

## 5. 询问导出内容

流程结束时，询问用户要导出哪些已完成内容：调研计划、市场调研、用户画像、机会点与风险，或全部调研内容。随后询问导出格式：

- 一个合并的 Markdown 文件，默认选项，适合 Obsidian
- 按模块拆分的多个 Markdown 文件
- Word 文档
- PDF 报告

导出内容应保留目录、来源链接、生成日期、研究范围和关键假设。询问保存位置；如果用户跳过，使用当前工作目录。用户选择 Word 或 PDF 时，使用当前环境可用的文档或 PDF 工具。如果环境无法生成所选格式，明确说明并提供 Markdown 作为替代方案。

## 表达规则

- 除非用户要求其他语言，否则默认使用中文。
- 先给结论，再给证据和对产品决策的意义。
- 用户画像每个主要结论章节紧邻结论提供对应图表与数据表；缺乏可用证据时用证据缺口表说明待补材料。其他模块按决策价值选择图表。
- 专业术语首次出现时给出简短解释。
- 明确区分已验证事实、用户观点、估算、假设和分析推断。
- 输出可执行的产品判断，不要只堆砌收集到的资料。
- 只在已定义的确认节点提问；能够合理推断的信息不要反复询问。

## 文档图表渲染

生成图表、矩阵、流程图或格式化表格前，阅读 [references/visualization-spec.md](references/visualization-spec.md)。数据图使用 ECharts，流程与关系图使用 Mermaid，表格使用 HTML＋CSS；复用宿主品牌主题。AI 输出声明式数据与证据，宿主负责渲染。无宿主协议时使用 `chart` JSON（`pm-chart-v1`）和 `mermaid` 围栏，并保留数据表与读图结论；不使用字符拼接图。定性矩阵用类别轴，不伪造精确数值。无数据时展示证据缺口。是否已渲染及导出能力按实际环境说明；全文 HTML 仍遵守原交付流程或宿主的按需生成规则。
